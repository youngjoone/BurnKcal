# 제품 방향: 한식 한 상에서 내가 먹은 양을 빠르게 기록

작성 기준: 2026-09-12. 아래 경쟁 기능은 공식 설명을 확인한 결과이며 직접 사용한 성능 비교가 아닙니다.
구현 상태 갱신: 2026-09-19. 실제 Gemini 분석·음식 보정·기기 저장·첫 프로필 등록·하루 목표·날짜별 달력·레시피 추천을 구현했습니다. 아래 표의 현재 상태와 [ROADMAP](ROADMAP.md)을 기준으로 구현과 실험 계획을 구분합니다.

출처에 적힌 정확도·속도 홍보 수치는 동일 조건으로 검증하지 않았으므로 비교 점수로 사용하지 않습니다.
일부 기능은 구독이나 플랫폼 조건이 있습니다. 이 문서는 가격 비교가 아닌 제품 범위 결정을 위한 것입니다.

사진만 보여주는 데모와 기록 습관을 만들 수 있는 제품의 가장 큰 차이는 **빠른 수정과 지속적인 저장**입니다.

## 3. 집중할 차별화 가설

**“사진 속 전체 음식이 아니라 내가 실제로 먹은 양을 기록한다.”**

대상은 여러 반찬과 국·밥을 함께 먹는 사람입니다. 경쟁 앱에 이 기능이 전혀 없다는 주장이 아니라, 이 상황에서 수정 시간을 줄이는 경험을 집중적으로 검증합니다.

### 가설 A: 한식 단위로 빠르게 수정

- 밥: 반 공기 / 한 공기 / 직접 입력
- 반찬: 먹지 않음 / 조금 / 보통 / 직접 입력
- 공용 음식: 전체 그릇과 내 섭취량을 구분. 인원수로 자동 균등 분할하지 않음
- 국·찌개: 건더기와 국물 섭취 정도를 구분하되 균일하게 절반 칼로리라고 계산하지 않음

‘조금’ 같은 단위는 숨겨진 정답이 아닙니다. 적용된 g 또는 인분 가정을 보여주고 변경할 수 있게 합니다.
동일한 음식 구성의 양 조절은 기본값에 비례 계산할 수 있지만, 국물·소스·건더기 비율 변경은 구성별 계산이 필요합니다.

### 가설 B: 많이 틀릴 수 있는 것만 한 번 확인

- 예: “이 반찬은 두부인가요, 계란인가요?”
- 예: “공유 음식 중 직접 먹은 양은 어느 정도인가요?”
- 중요한 불확실성이 있을 때 선택 가능한 질문을 최대 하나 먼저 제시하고, 건너뛰기도 제공
- 모델이 말한 자신감 수치를 검증된 정확도 확률처럼 표시하지 않음

질문 자체는 Cronometer의 숨은 재료 제안 등과 겹칩니다. 차별화 가설은 질문 수를 제한하면서 한식 기록의 수정 부담을 줄이는 데 있습니다.

### 가설 C: 수정한 내 기준을 기억

사용자가 동의하면 ‘내 밥그릇 한 공기’, 자주 먹는 반찬의 수정값을 기기에 저장합니다.
다음 식사에서 이전 값을 제안하되 사진이 비슷하다는 이유로 자동 확정하지 않습니다.
처음부터 모델 학습이나 사진 서버 저장을 할 필요는 없습니다.

## 4. 신뢰와 비용을 함께 다루는 구조

후보 구조: **Gemini가 음식 후보·양 가정 추정 → 영양 DB 후보 매칭 → 사용자가 확인 → 서버가 항목과 총합 계산**.

현재 `FoodAnalyzer`에는 데모와 Gemini 구현이 있습니다. Gemini의 음식별 추정값을 검증·합산하고 사용자가 수정하여 저장합니다. 분석한 식사의 영양 DB 매칭은 미구현입니다. 기본 레시피 6종은 USDA 자료에서 계산하고 실시간 추천은 Gemini 추정값을 표시합니다.
[식약처 K-FIND](https://various.foodsafetykorea.go.kr/nutrient/)는 식품 검색·영양성분 데이터 다운로드·Open API 안내를 제공합니다.
도입 시 사용 조건, 갱신 주기, 100g/1회 제공량 단위, 조리 방식과 매칭 범위를 확인합니다.
DB에 없거나 애매한 음식은 ‘AI 추정’으로 구분하고, 근거 없이 DB 값으로 표시하지 않습니다.

공개 DB에 연결해도 사진의 양 추정과 가려진 기름·소스 문제는 남습니다.
정확도를 높이려면 DB 선택과 별도로 양 수정 UX와 검증 샘플이 필요합니다.

현재 Gemini 3.1 Flash-Lite를 사용합니다. 같은 사진으로 더 강한 모델과 비교하고 실패율·지연·재요청을 포함한 ‘완료한 기록 한 건당 비용’으로 선택합니다.
양만 수정할 때는 매번 AI를 재호출하지 않고 확인된 기준값으로 재계산합니다.

## 5. 화면 방향

- **첫 실행:** 신체·목표 → 생활 정보 → 목표 확인의 3단계. 저장 후 반복 입력 없음
- **오늘:** 목표·섭취·잔여량과 촬영/앨범 버튼, 다음 한 끼 추천
- **기록:** 월별 달력에서 날짜별 식사 조회·추가·수정·삭제·복구
- **설정:** 프로필과 제외 재료·조리 시간 변경
- **사진 확인:** 자르지 않은 전체 사진, 선택 설명, 전송 버튼
- **결과 확인:** 총합 → 음식별 카드 → 항목 수정 → ‘이 식사 저장’
- **기록 상세:** 사용자가 확정한 음식·양·칼로리, 다시 수정·삭제 가능. 수정 이력 보관은 추후 확장

기본 스타일은 밝은 중립 배경, 단일 녹색 포인트, 얇은 경계, 일관된 여백입니다.
우선 사진·음식명·양·칼로리를 읽기 쉽게 만들고, 장식·애니메이션은 흐름을 방해하지 않을 때 추가합니다.
사진 위 음식 위치 표시나 탭 선택은 모델의 위치 정보 정확도를 검증한 뒤 고려합니다. 가짜 위치 박스를 그리지 않습니다.

## 6. 검증할 성공 기준

아래 수치는 성능 약속이 아니라 초기 실험 목표입니다.

1. 소규모 사용성 테스트: 목표 사용자 5명이 촬영 후 수정·저장을 도움 없이 완료하는지 확인.
2. 기록 속도: 같은 식사에서 일반 검색 입력보다 중앙 완료 시간을 30% 이상 줄이는지 비교. 네트워크 시간과 사람의 조작 시간을 분리.
3. 음식 인식: 단품·한식 정식·공유 반찬·국물·가림·비음식이 포함된 30~50장부터 시작. 음식별 누락·중복·오인식을 측정.
4. 칼로리: 재료와 중량이 알려진 별도 샘플에서 음식별/식사별 오차를 측정. 사용자 수정값을 자동으로 영양 정답으로 간주하지 않음.
5. 개인화: 같은 음식의 두 번째 기록에서 수정 횟수가 줄어드는지 확인.
6. 비용: 실패와 재시도를 포함한 저장 1건당 토큰 비용, 분석 응답 p50/p95, 오류율을 기록.

확인되지 않은 ‘정확도 95%’, ‘모든 음식 인식’, ‘업계 최초’ 문구는 사용하지 않습니다.
